# 에픽 초안 — 사람과 여러 클라이언트

**상태: 초안. 착수 전.** PM 요청으로 잡는다 (2026-08-19).

지금 무엇이 박혀 있고, 무엇으로 바꾸며, 어떤 순서로 쪼개는지만 적는다.
설계 결정은 PM 승인 전까지 확정이 아니다.

## 왜 지금 쓰나

같은 빈자리가 두 번 드러났다.

1. **HQ** — 구성원이 역할이 아니라 소집된 방의 lead다. 역할 보유로만 보면 전원이
   막혀서 `workspace_participant`에 특례 분기를 넣었다
2. **보조인력(PM2)** — 사람을 방 하나에만 넣을 수단이 없다. 사람은 참가 검사를
   통째로 우회한다

**두 번 특례면 그건 개념이 빠진 것이다.** 빠진 개념은 **참가**다.
`db.py:601`의 주석이 스스로 그렇게 말한다.

> 참가 = 역할 보유로 본다. 지금 모델에서 방에 있다는 것을 말하는 다른 수단이 없다

## 지금 모델이 말없이 가정하는 것

| 가정 | 어디서 깨지나 |
|---|---|
| 사람은 하나뿐이다 | 보조인력 투입 |
| 그 사람은 모든 방을 본다 | 방 하나만 맡기고 싶을 때 |
| 방에 있다 = 역할을 갖고 있다 | HQ (이미 깨졌다) |
| 에이전트에게 답한다 = PM에게 간다 | 사람이 둘일 때 |
| 클라이언트는 한 대다 | 윈도우·맥 병행 |

## 실제로 박힌 자리

코드에서 확인한 것만 적는다.

| 자리 | 지금 | 문제 |
|---|---|---|
| `db.py:623` | `kind == "human"`이면 무조건 통과 | 사람이 늘면 전원이 전부를 본다 |
| `db.py` `workspace_participant` HQ 분기 | HQ만 규칙이 다르다 | 참가가 없어서 생긴 특례 |
| `db.py:1544` `assign_role` | `kind = 'agent'` 요구 | 사람이 역할을 잡을 수 없다 |
| `role_assignments.agent_id` | 칸 이름은 agent, FK는 `principals` | 스키마는 이미 사람을 받는다 |
| `agent_cli.py:805` `default_recipients` | `[pm_id]` 하나 | 답이 누구에게 갈지 안 정해진다 |
| `registry.py:153` | 노드마다 `pm-<nodeid>`를 새로 만든다 | **기기가 둘이면 같은 사람이 둘이 된다** |

마지막 것이 다중 클라이언트의 진짜 지뢰다. 두 번째 기기에서 처음 뜨는 순간
새 PM principal 이 생긴다. 사람이 아니라 기기를 세고 있다.

**반대로 이미 되어 있는 것도 있다.** `client_nodes` 테이블이 있고
`agent_bindings.node_id`가 그것을 가리키며, UNIQUE 가
`(node_id, terminal_provider, terminal_session_id)`라 노드별로 갈린다.
**서버는 이미 여러 노드를 전제한다.** 못 하는 것은 사람 쪽이다.

## 목표 모델

```
membership(workspace_id, principal_id, ...)   ← 방에 있다
  └ 역할                                       ← 그 방에서 무엇을 하는가
     └ lead                                    ← 그 역할이 방을 대표한다
```

세 줄이 전부다.

- **참가가 일급이 된다.** 사람이든 에이전트든 같은 규칙으로 방에 있다
- **역할은 참가 위의 이름표다.** 지금처럼 참가를 대신하지 않는다
- **PM은 소유자다.** 전 방 참가를 갖는다. 특권이 아니라 데이터가 된다
- **HQ 특례가 사라진다.** 소집이 곧 membership 을 만든다
- **`workspace_participant`가 한 줄 조회가 된다.** 코드가 느는 게 아니라 준다

사람과 에이전트를 같은 규칙에 놓을 수 있게 되는 것이 여기서 온다. 지금은 사람이
규칙 밖이라 PM2 를 넣을 자리가 없었다.

### 클라이언트 쪽

사람은 principal 하나, 기기는 여럿. 노드가 사람을 만들지 않는다.

```
사람 (principal)
 └ 노드 A (맥)      ← client_nodes 에 이미 있다
 └ 노드 B (윈도우)
```

노드는 자기 id 만 갖고, PM principal 은 서버에서 받거나 설정으로 주입한다.

## 쪼개기 — 에픽의 잎

순서가 있다. 앞이 뒤의 전제다.

| | 잎 | 닫힘 판정 |
|---|---|---|
| 1 | `membership` 도입 + 백필 (역할 보유자·HQ lead·PM 전 방) | 기존 방 전부에서 참가자 목록이 지금과 같게 나온다 |
| 2 | `workspace_participant`를 membership 조회로 교체 | human 특례와 HQ 분기 둘 다 지워진다 |
| 3 | 사람도 역할을 잡을 수 있게 (`assign_role` 검사, 온보딩 안내 걸러내기) | 사람에게 `fungis init` 안내가 안 간다 |
| 4 | `reply` 기본 수신자를 방 기준으로 (그 방 사람 역할 → 없으면 PM) | 방마다 답이 다른 사람에게 간다 |
| 5 | 노드가 PM principal 을 새로 만들지 않게 | 두 번째 기기에서 같은 사람으로 붙는다 |
| 6 | 승인 층위 명시 (r2 위임 가능 여부, r3 는 소유자) | 문서와 코드가 같은 말을 한다 |

**백필은 새로 물어볼 것이 없다.** 전부 지금 데이터에서 유도된다.

1·2가 이 에픽의 값 전부다. 3~6은 그 위에서 각각 짧다.

## 안 하는 것

- **읽기 경계를 좁히지 않는다.** 보조인력은 PM이 부른 사람이고, 읽기를 막으면
  도울 수가 없다. membership 은 "누가 여기 있나"를 표현하는 것이지 담을 치는
  것이 아니다. 담이 필요해지면 그때 membership 위에 얹는다
- **인증은 이 에픽이 아니다.** non-loopback 서버와 credential 은 `PRODUCT_SPEC`
  12장 M1 이다. 다중 클라이언트가 한 서버를 보려면 그것이 선행이지만 별개다
- **`role_assignments.agent_id` 개명은 안 한다.** 참조가 넓고 값이 작다.
  membership 이 들어오면 그 칸의 뜻이 저절로 좁아진다

## PM 이 정한 것 (8/19)

- **보조인력은 PM 과 동등한 권한이 기본이다.** `r2`·`r3` 를 사람에 따라 가르지
  않는다. 잎 6("승인 층위 명시")은 사람별 차등이 아니라 **전이별 층위**만 적는
  일로 좁아진다
- **보조인력은 윈도우 작업자다. 추후 WSL 환경까지 본다.** 그래서 이 에픽만으로는
  안 끝난다 — 앱이 SwiftUI 라 윈도우에 PM 화면이 없고, 두 기기가 한 서버를 보려면
  `PRODUCT_SPEC` 12장 M1 인증이 선행이다. 잎 5(노드가 PM principal 을 새로 안
  만들게)가 그 첫 조각이다

## 미결

- 소집(HQ)이 membership 을 만든다면, 소집 해제가 그것을 지우나 남기나
- PM 이 전 방 참가를 데이터로 갖는다면 방을 새로 만들 때 자동으로 붙는가
