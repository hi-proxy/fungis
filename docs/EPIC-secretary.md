# 에픽 초안 — 비서

**상태: 초안. 착수 전.** PM 발상 (2026-08-19), 이 문서는 받아 적은 것이다.
설계 결정은 PM 승인 전까지 확정이 아니다.

**`mei` 라고 부르지 않는다.** 완성형 mei 와 구분이 안 된다. 이 문서에서는 비서다.

## 왜 만드나 — PM 의 말

> 요즘 내가 거의 코드리뷰를 못 해서. 이렇게 조금씩이라도 해서 블랙박스를
> 줄이려고 해.

**목적은 요약이 아니라 블랙박스를 줄이는 것이다.** 그래서 넓게 훑는 것보다
좁게 파고드는 쪽이 값이다. 하루에 기능 1~2개를 라인까지 보는 것이, 그날 있었던
일 열 개를 훑는 것보다 낫다.

이 한 줄이 아래 모든 선택의 기준이다. 무엇을 만들지 헷갈리면 여기로 돌아온다.

## 무엇인가

| | |
|---|---|
| 범위 | **전역.** 방 하나에 매인 참가자가 아니다 |
| 접근 | 전체 채팅 |
| 제1역할 | 그날 전체 프로젝트 진행 중 **기능 1~2개**의 코드 리뷰 |
| 산출 | **라인 안내와 함께 코멘트** |
| 자리 | 전역 레이아웃에 상태 표시 · 대화는 **따로 채팅방** |

## 고르는 규칙은 미리 못 박지 않는다

무엇을 리뷰할지가 이 기능의 값을 결정한다. 처음에 위험도(되돌릴 수 있는가)를
축으로 제안했으나 **PM 이 거절했다.**

> 꼭 위험도로 잡지 않아도 돼. 그냥 블랙박스를 줄여가는 것 자체에 의미가 있음.

그래서 규칙을 앞에서 정하지 않고 굴려 보며 정한다. 후보는 적어 둔다 — 되돌리기
어려운 것 · 그날 닫힌 티켓 · PM 이 아직 안 본 것 · 변경이 큰 것. 어느 것이
블랙박스를 실제로 줄이는지는 **몇 번 돌려 봐야 안다.**

이것은 루프 설계와 같은 태도다 — "시행착오가 분명히 있을 것이므로 도입 시기를
당기는 것이 먼저다."

## 새로 만들 것이 적다

비서가 필요로 하는 것은 대부분 이미 이름이 붙어 있다.

| 필요 | 어디에 있나 |
|---|---|
| 전체 채팅 접근 | [EPIC-participation.md](EPIC-participation.md) — 지금은 사람만 전 방을 본다 |
| 주기로 도는 것 | `LOOP.md` 의 `wake --in` / `next_wake_at`, 또는 mei 의 웨이킹 |
| 리뷰 대상 저장소 | `project_repositories` 가 방마다 이미 물고 있다 |
| 기억 | mei 의 몫. 시간 축으로 깊게 |
| 관찰자 규범 | `LOOP.md` 의 리뷰어 배석 |

**mei 는 이미 하네스를 갖고 있다** — 2초 폴링, `next_wake_at`, 예산, 기억.
fungis 가 스케줄러를 새로 만들 필요가 없다.

### 리뷰어 배석과 같은 모양이다

`LOOP.md` 가 리뷰어에게 건 조건이 비서에게 그대로 맞는다.

- 리뷰어는 일하지 않는다. 고치기 시작하면 worker 가 둘이 된다
- 리뷰어는 추론 과정을 보지 않는다. 결과만 본다
- 판정이 구조화된 값이어야 한다. 산문이면 답장 릴레이가 재현된다

**비서는 턴 단위가 아니라 하루 단위로 도는 리뷰어다.** 규칙을 새로 만드는 것이
아니라 그 절의 주기를 바꾸는 것으로 보인다.

### 2단계의 첫 실사용자다

`LOOP.md` 2단계는 binding 을 transport / liveness / state 로 쪼개는 일이다.
지금까지 그것을 요구한 것은 mei 자신뿐이었고, mei 는 파일 채널로 우회해도
살아남았다. **가설이었다.**

비서는 다르다. PM 이 원해서 생기고, 터미널이 없고, 상주하며, 주기로 돈다.
2단계가 만들려던 모양이 정확히 이것이다.

## 전역 상태 표시 — `(state, next_wake_at)` 의 첫 소비자

PM 이 요구한 것은 셋이다.

```
활성인지 슬립인지
나에게 할 말이 있는지
접든 펼치든 항상 같은 자리에      ← 앱 헤더의 상시 프로필 옆
```

앞의 둘이 곧 어댑터 경계에 놓기로 논의한 값이다. mei 가 이미 매 틱 파일로 쓴다.

```
state          sleeping | waking
next_wake_at   언제 반응하나
pending        아직 안 겪은 것
```

**그 값이 없으면 이 띠를 못 그린다.** `LOOP.md` 에 `(state, next_wake_at)` 을
넣을지 묻고 있는 것이 이 자리다 — 쓸 데가 생겼다.

`할 말 있음` 은 `pending` 의 반대 방향이라 하나 더 필요하다. 비서가 PM 에게 보낼
것을 쌓아 두었다는 표시다. **인박스로 밀지 않고 표시만 하는 것**이라
`later`·`silent`([CLI.md](CLI.md))과 같은 결이다.

## 따로 채팅방

HQ 와 같은 모양이면 방 기계를 그대로 쓴다. HQ 는 만들지 않는다 — 처음부터
목록에 있는 프로젝트 위의 방이다. 비서 방도 `kind` 하나 더 두면 된다.
**새로 만들 것이 없다.**

## 라인 안내 — 눌러서 갈 데가 없다

비서가 `file.py:120` 이라고 적어 줘도 지금 앱은 본문을 그냥 글로 그린다. PM 이
손으로 찾아가야 한다. 그러면 블랙박스가 그만큼 덜 줄어든다.

PM 이 물었다 — 코드 파일을 앱에서 직접 띄우면 IDE 가 되어 공수가 크게 늘지 않나.
**둘로 갈린다.**

| | 무엇 | 값 |
|---|---|---|
| 읽기 전용 한 장 | 파일을 그리고 그 줄로 스크롤 | 작다. 저장소 경로를 이미 방마다 들고 있다 |
| 편집·검색·git 통합 | IDE | 하지 않는다 |

비서가 짚어 준 줄이 눌러서 보이는 것까지면 목적에 닿는다. 그 이상은 쓰던
편집기로 가는 편이 낫다.

## 순서

1. **참가 에픽** (`FUNG-3`~`FUNG-8`) — 비서가 전 방을 보려면 이것이 먼저다
2. **`(state, next_wake_at)`** — 전역 띠가 이 값을 그린다
3. **2단계 binding 쪼개기** — 터미널 없는 상주 참가자를 앉힌다
4. 비서 자신 — 방 `kind`, 전역 띠, 리뷰 도는 것
5. 읽기 전용 파일 보기 — 라인 안내가 실제로 값을 내려면

**1~3 이 이 문서보다 앞이다.** 비서는 그것들이 끝나면 얇게 얹히는 것이지,
따로 크게 만드는 것이 아니다.

## 미결

- 요약·리뷰를 비서 방에만 남기나, 각 프로젝트 방에도 남기나. 방에 남기면 비서는
  참가자고 PM 에게만 보고하면 관찰자다. 열람 경계가 여기서 갈린다
- 비서가 다른 에이전트에게 말을 거나. 하면 그들이 반응하게 되고, 안 하면 PM 만
  읽는 일지가 된다
- 리뷰 대상을 고르는 규칙 — 굴려 보며 정한다 (위 참고)
